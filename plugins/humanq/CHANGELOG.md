# Changelog

## 0.21.0

### 追加

- 画面に「見通し」のタブを足した。ヘッダーの下のタブ「判断待ち / 見通し」の 2 つ目で、既定で開くのは今までどおり判断待ち (ページを開くたび。選んだタブは覚えない)。見通しは読むだけの画面で、登録したプロジェクトごとに、状態別の件数と、次に着手できるチケット (ready) の上位 5 件 (優先度 → 作成日の順。全件数も出す) を出す。上部には判断待ちの件数 (ヘッダーと同じ数) と、判断待ちのタブへのリンクを出す。タブは矢印キー・Home・End でも移れる
- 次に着手できる一覧からは `answered` の付いたものを除き (README の「作業を選ぶ一覧からは `answered` も除く」と同じ)、`human` の付いたものには「判断待ち」の印を付けて、題を判断待ちのカードへのリンクにする (押すと判断待ちのタブのそのカードにフォーカスが移る。保留中のカードなら畳んだ節を開き、絞り込みで隠れていれば絞り込みを解く。判断待ちに無ければ知らせて読み直す)。ready の行にラベルが無い CLI でも効くよう、判断待ちの読みのキャッシュにある id (判断待ち・保留中・回答済み) も使う (CLI は打ち足さない)
- ラベルは humanq 自身のもの (`human` / `answered` / `snoozed`) を除いて文字列のまま出すだけで、並びにも使わない (`plugin:` や `lane:` などのラベルを解釈しない)。見通しにはボタンも書き込みの部品も置かない (優先度の変更・着手・close はしない)
- サーバーに `GET /api/overview` (`?project=<パス>` でそのプロジェクトだけ) を足した。画面が見通しのタブを開いたときだけ読み、1 プロジェクトあたり 2 プロセス (bd は `bd count --by-status --json` と `bd ready --limit 0 --json`、br は `br count --by status --json` と `br ready --limit 0 --json`)。読みは判断待ちと同じプロジェクトごとのロックの下で 1 本ずつ行い、キャッシュは判断待ちとは別に 60 秒。回答・取り消し・保留・保留の解除の後は、判断待ちのキャッシュと一緒に捨てる
- bd と br の差は backend の層 (`server/backend.py`) の `status_counts` と `ready` が吸収する。出力の形が崩れたとき (JSON でない・groups が list でない・件数が 0 以上の整数でない・ready が配列でない) は、そのプロジェクトの見通しだけを読めないことにして理由を出す。ready の要素のうち id の読めないものは落とす

- 判断待ちを主役に保つ: `/api/items` (15 秒ごとのポーリング) と `/api/summary` (hook) は見通しを読まず、見通しのデータ (状態別の件数・ready) を含めない。SessionStart と UserPromptSubmit の hook も見通しを読まない。ヘッダーの件数・タブのタイトル・デスクトップ通知・hook の件数は、今までどおり判断待ちだけを数える

## 0.18.1

### テスト

テストの偽の bd・br (`tests/fake_beads.py`) を本物 (bd 1.3.4・br 0.7.6) に合わせた。製品コード (`server/`・`hooks/`) は変えていない (挙動の変更なし)。偽物のほうが本物と食い違うと、偽物の上で緑のテストが本物では別の経路に入る。

- 偽の br の `show --json` は、コメントの無いチケットで `comments` の key を出さない (前は `[]` を出していた。本物の 0.7.6 は 0 件のとき key を出さない)。読む側 (`backend.br_thread`) は key の無い show を 0 件と読む。契約テストの「コメントの無い show」を「無いか空」から「key が無い」に締め、コメントを書いた後は出ることも確かめる。偽物にも本物にも通す
- 偽の br は `update --agent-context` の JSON を、本物と同じく詰めて (空白を除き、escape を正規化し、key の順は保つ) 保存する。半分未満の判定は詰めた後の長さで行う。偽物は JSON でない値をそのまま保存する (本物は exit 7 で断る。偽物が寛容な側の食い違いで、そのまま残した)。契約テストに「詰めて返る」を足した (inline と `@file`、show と list)
- 偽の bd の `comments add <id> -f <file> --json` は、書いたコメントを JSON で返す (前は 1 行の案内文)。humanq は `--json` を付けない。契約テストに 1 件足した (戻りは書いたコメント 1 件の object。本物の bd 1.3.4 で測った。本物は `schema_version` も返すが、偽物は出さない)
- 偽の br が本物より厳しかった 4 つの形を、本物に合わせて通すようにした。契約テストは、偽物が断る形の表 (`REFUSED`) と対になる、本物が通す形の表 (`ACCEPTED`) を持つ:
  - `show` に id 無し: 最後に触ったチケット (create・update・close・label・comments add が記録する。show・list・comments の読み・ほかのチケットの delete は記録を変えない。最後に触ったチケットを delete すると記録が消える) を出す。記録が無ければ `VALIDATION_FAILED` (exit 4)
  - `label add` / `label remove` に label が 2 つ以上: 1 個ずつ処理し、label ごとに 1 行を返す。id が無ければどれも処理しない
  - `comments add <id> x -f <file>`: `-f` があれば本文の位置引数は無視し、ファイルの本文で書く (id の位置は問わない)
  - `close <id> -r` (後ろに `--json` が付く形): `close` の `--reason` (`-r`)・`create` の `--description` (`-d`)・`update` の `--notes` は、次の語が `-` で始まっても値に取る (subcommand ごと。`delete` の `--reason` は取らない: `delete <id> --reason --json` は本物も exit 2)。`--json` が理由になって閉じる。`-r` が最後の語なら usage エラー (本物も exit 2)
- 偽の br の usage エラーの分岐 (`raise Usage(`) の全部を、`REFUSED` の形のどれかが踏むことを確かめるテストを足した (`FakeBrUsageBranches`)。偽物を進程内で動かして断りが上がった行を集め、ソースの分岐 (ast) と比べる。分岐を足して `REFUSED` に形を足し忘れると落ちる。後ろに `--json` を付けると断られない形 (`--actor`・`close -r` の値無し) は、何も付けない形の表 (`REFUSED_AS_LAST_WORD`) に分けた。`-C`・知らない subcommand・`comments add -f` に id 無し (在るファイルで試す。無いファイルだと、id でなくファイルのせいでも断られる)・`delete --reason` に値無しの行を `REFUSED` に足した。このテストが数えるのは `raise Usage(` と `raise br_usage_unexpected(` の字面だけで、別名を介した raise と usage でない断り (`Fail` 系) は対象外
- 偽物は、まだ本物と食い違う形が残る: 後ろに何も付けない `update` と `close` (id 無し) は本物では最後に触ったチケットに効くが、偽物は断る (`--json` を付けると本物も断る)。humanq は使わない形

## 0.18.0

### 画面

- 一覧を status で絞らないのは、利用者が `br list -l human` で見る判断待ちと同じものを画面と hook の件数に出すため。br 0.7.6 の `list` の既定は `closed` と `tombstone` (`br delete` したもの) だけを除き、`deferred`・`draft`・`pinned` と、`br update --status` が宣言なしで受け付ける独自の status (`review`・打ち間違いの `in-progress` など) を含む。bd の回答済みの読みと同じ 4 つの status (`-s open -s in_progress -s blocked -s deferred`) で絞ると、それ以外の status の判断待ち・回答済みが画面と hook の件数から黙って消える (マージ前レビューの指摘)。`--limit 0` と途中で切れた一覧 (`has_more`) の扱いは、絞らなくても変わらないことを本物で確かめた
- `show` は ID が 1 つでも無いと全体が exit 3 で失敗する。一覧から `show` までの間にチケットが消えたときのために、exit 3 なら一覧から 1 回だけ読み直し、それでも失敗したらそのプロジェクトを読めないことにする (exit 3 以外の失敗は読み直さない)
- 問いは `show` の `agent_context` (JSON の文字列) の top-level の key `humanq` から読む。形と正規化 (問いの署名 `qsig` の作り方を含む) は bd の metadata の `humanq` と同じ。`agent_context` が JSON の object でない・空・`humanq` が無い・`ask` が文字列でないときは「問いが未整理」(q=None)。一覧の `agent_context` は読まない (br の schema の文書が「list には出ない」としているため、文書の側に寄せた)
- 親から継いだ agent_context は問いにしない。br は `.beads/config.yaml` の `inherited_context.enabled` で、親の `agent_context` を子の `show` の別の key `inherited_context` に出す (子の `agent_context` には入らない。br 0.7.6 で実測)。humanq は `agent_context` だけを読むので、子のカードに親の問いと署名は出ない
- 問いの値 (`humanq`) が JSON の文字列で、入れ子が深くて json の parser が `RecursionError` を上げるときも「問いが未整理」にする。今までは例外がプロジェクトの読みまで抜けて、その 1 件でプロジェクトの全チケットが読めなくなっていた。bd の metadata の `humanq` が同じ形の文字列のときも同じ関数を通るので、bd のプロジェクトでもそうなる (マージ前レビューの指摘)
- br はコメントの並びが決まっていない。`show` の `comments` を `created_at` の順 (同じ秒なら単調に増える ID の順) に並べてから、最後の `[humanq]` コメントを回答の本文・回答の署名 `asig`・両ラベルのチケットの向きに使う。時刻や ID の読めないコメントは古い側に置く。`comments` が無い (br はコメントの無いチケットで key を出さない) のは 0 件、list でないのは「読めない」(回答の署名が空)
- 一覧が envelope (`{"issues": [...]}`) でない・JSON でない・途中で切れている (`has_more`)・ID が文字列でないか `-` で始まる (show の引数で flag に読まれる)、`show` の出力が list でない・頼んだ ID が欠けている、はどれもそのプロジェクトを読めないことにする (ほかのプロジェクトは読める)
- br はプロジェクトの dir を cwd にして起動する (br に `-C` は無い。プロジェクトごとに版を切り替える仕組みも、そのまま効く)。DB・`.beads`・JSONL の場所を指す env (`BEADS_DB`・`BD_DB`・`BD_DATABASE`・`BEADS_DIR`・`BEADS_JSONL`) は br に渡さない。br 0.7.6 で、`BEADS_DB` と `BEADS_DIR` が cwd より優先され、別のプロジェクトの DB を黙って読むことを確かめた
- br を起動できないときは「br を起動できない (PATH を確認): …」、時間内に終わらないときは「br が 60 秒で終わらない」を、そのプロジェクトのエラーにする

- `server/registry.py` に `project_kind(root, cli)` を置いた。`.beads/` の中のファイルの印だけで `bd` / `br` / `unknown` / `conflict` と理由を返す (CLI は打たない。hook とサーバーの両方が使う)。br の印: `.beads/.gitignore` の `.br_history` か `fsqlite` を含む行 (コメント行は読まない)・`.br_history/`・`*-fsqlite-ns-*`・`.br-db-*.lock`。bd の印: `metadata.json` の `database` か `backend` が `dolt`・`embeddeddolt/`。br の印だけなら br、bd の印だけなら bd、両方なら conflict、どちらの印も無く `metadata.json` の `database` が `.db` で終わるなら unknown、どれにも当たらなければ bd (今までどおり)。`issues.jsonl` の有無は使わない
- 明示の設定として、hook の env `HUMANQ_BEADS_CLI` (`bd` / `br` / `auto`、未設定は `auto`。前後の空白と大文字小文字は無視) を足した。指定に反する印があれば conflict、無ければ指定どおり。SessionStart の hook が `projects.json` の各 entry に `"cli"` (指定か null) も書き、サーバーはこの値と印で決める。不正な値は `auto` として扱い、SessionStart の出力に 1 行だけ警告する
- unknown・conflict・br のプロジェクトでは、どの CLI も起動しない。`/api/items` の各プロジェクトは `ok:false`・`writable:false`・`error` を返す (unknown・conflict は「bd と br のどちらで読むか決められない (理由)。`HUMANQ_BEADS_CLI` で指定してください」、br は「br のプロジェクトにはまだ対応していません」)。br を bd の `.beads/` に向けて打つと、エラーを出さずに空の一覧を返して `.beads/` に dolt のファイルを作るので、br は br と確定した dir にだけ打つ前提にしている
- `/api/items` の各プロジェクトに `cli` (`bd` / `br` / `null`) と `writable` を足した (既存の key は変えていない)。bd として読むプロジェクトは、読みに失敗しても `writable:true`
- `POST /api/answer`・`/api/undo` は、`writable:false` のプロジェクトに対して CLI を打つ前に 400 `{code: "readonly", op}` を返す
- `/api/summary` に `ok` と `error` を足した (既存の key は残す)。今までは読めなかったプロジェクトも `human: 0` を返し、hook が「判断待ち 0 件」と言ってしまっていた。hook は `ok:false` のとき「このプロジェクトの判断待ちを読めない: <error>」と伝え、件数は言わない。UserPromptSubmit は読めなかった応答で、伝えた回答の記憶を消さない
- 設定や印が変わったときは、キャッシュの時間内でも読み直す (ファイルを見るだけ)

### 変えていないもの

- bd のプロジェクトの読み書き・bd の argv・画面・CSP は変えていない (サーバーが打つ bd の argv の列の固定は、テストを変えずに通る)。画面のバナーの文言は 0.8.0 で CLI に依らない形になっている

### テスト

- `tests/test_project_kind.py` を足した。判定の各行 (br の印 4 種と、`.gitignore` の 2 語・bd の印・両方・印なしの SQLite の形・何も無い形・`issues.jsonl` だけ・コメント行だけの `.gitignore`・明示の 3 値と不正値) を 1 件ずつ、偽の bd・br を PATH に置いて、bd の形の dir では br が 1 回も呼ばれないこと、br・unknown・conflict ではどの CLI も呼ばれないこと、`HUMANQ_BEADS_CLI=br` を bd の形に向けると conflict で `.beads/dolt` が作られないこと、`writable:false` への POST が CLI を呼ばずに 400 readonly になること、summary の `ok:false`、hook の出力が「0 件」と言わないこと、不正値の警告が 1 行だけなことを固定した

## 0.7.0

### 画面とサーバー

- 回答の取り消しで、取り消す回答を照合するようにした。今までは、別のタブで取り消して答え直した後に、このタブに残っていた前の回答の成功のトーストの「取り消す」を押すと、今の回答 (別のタブで答え直したもの) が取り消されていた。サーバーの `/api/undo` がチケットだけを見て、最後の `[humanq]` 回答を取り消していたため。タブが隠れている間はトーストの表示時間が進まないので、この窓は 6 秒に限られなかった。このタブを通らない変化 (別のタブ・ほかのセッションでの取り消しと答え直し) では、前の回答のトーストを閉じる処理も走らない。回答済みのカードの「取り消して判断待ちに戻す」も、15 秒ごとの読み込みの前に押せば同じことが起きえた
- `/api/answer` の成功の応答に、回答の署名 `asig` を入れる (`{ok: true, asig}`)。回答済みの一覧 (`/api/items` の `answered`) の各チケットにも、最後の `[humanq]` コメントの署名 `asig` を入れる。署名は、そのコメントがチケットの何件目の `[humanq]` コメントかと、その本文から作る (同じ選択肢での答え直しも前の回答と分ける。エージェントのコメントは数えないので、間に挟まっても変わらない)。送り直し (コメントを書かずにラベルだけ直す) の応答には、残っている回答の署名を返す。照合は今までの読みに相乗りし、bd の呼び出しは増やしていない
- 画面は、トーストの「取り消す」では成功の応答の署名を、回答済みのカードでは一覧の署名を `/api/undo` に付けて送る。サーバーは今の最後の `[humanq]` コメントの署名と照合し、違えば何も書かずに 409 `{code: "stale", op: "undo"}` を返す。画面は「取り消しませんでした。この回答はもう最新ではありません (ほかで答え直されています)」と知らせ、カードを戻さずに読み直す (回答済みのカードが今の回答で出直す)。そのチケットの前の回答の成功のトーストも閉じる
- 回答済みのカードの表示の署名に `asig` を入れた。同じ本文で答え直された回答でも、読み直しでカードが作り直され、取り消しが今の回答の署名を送る
- 一覧でコメントを読めなかったチケットの署名は空にし、どの回答とも合わないようにした (そのカードからの取り消しは断られ、読み直すと直る)。画面は署名が分からないときも空の署名を付けて送る (付けないと、署名を送らない古い画面と同じに読まれて照合されない)
- `asig` を送らない古い画面 (更新の前から開いたままのタブ) の取り消しは、今までどおり照合せずに受け付ける
- 取り消しのラベルの付け替えが途中で失敗した後に、同じ回答の署名で取り消し直すと 409 になる (最後の `[humanq]` コメントは取り消しのコメントで、回答の署名と合わない)。画面からはこの経路に届かない (失敗の後、チケットは判断待ちに出て、回答済みのカードもトーストも残らない。答え直せばラベルは直る)
- `[humanq]` のコメントを数えるとき、本文が文字列でないコメントは数えない (回答の書き込みは全部のコメントを数えるので、想定外の形の 1 件で回答を止めない)

### できること

- bd (beads) の判断待ち (`human` ラベル) を、端末の全プロジェクト分まとめて `http://127.0.0.1:8765/` の画面に出す。問いは metadata の `humanq` (問い・背景・選択肢・推奨) から描き、無いチケットは本文と自由記述欄だけを出す
- 画面で答えると、`[humanq] 回答: <label> (<key>)` のコメント (作者 `user/humanq`) を書き、`human` を `answered` に付け替える。close はしない。反映前なら取り消せる
- SessionStart: cwd から上に `.beads/` があるプロジェクトだけを登録し、サーバーが無ければ切り離して起動する。複数のセッションが同時に起動しても 1 台になる。判断待ちと回答済みの件数を Claude に伝える
- UserPromptSubmit: そのセッションで前に伝えた後の新しい回答を Claude に伝える (サーバーのキャッシュを見るだけで bd は読まない)

### 画面の動き

- 「回答する」を押すとすぐにカードを畳み、送信は裏で行う。失敗したら読み直してから戻すかを決め、書き込まれていなければ赤い枠で戻す。ほかで回答済みなら戻さない
- 描き直しはカードを key ごとに使い回す。押している最中のボタン・フォーカス・開いた本文・入力中の下書きを作り直さない。入力中のカードの更新は後回しにし、問いが変わっていれば送る前に作り直して知らせる
- 下書きは再読み込みしても残る (sessionStorage)。reduced-motion では動きを止め、失敗の目印は静的な枠で残す

### 書き込みの安全

- 待ち受けは 127.0.0.1 だけ。書き込みは、画面に埋め込んだトークンと Host の検査を通ったものだけ。CSP で外部の読み込みを禁じ、`frame-ancestors 'none'` と `X-Frame-Options: DENY` で他のサイトの iframe に入れさせない
- トークンは state dir のファイル (0600) に保存し、サーバーを入れ替えても変えない
- 送り直しで回答を二重に書かない (最後のコメントが同じ本文の `[humanq]` で 10 分以内なら、ラベルだけ直す)。ラベルの付け替えは 1 回だけ再試行し、失敗した段階と送信の種類を応答に入れる
- 見ていた問いの署名 (`qsig`) を回答に付け、問いが書き換わっていれば書き込まずに 409 を返す
- `human` と `answered` が両方付いたチケットは、最後の `[humanq]` コメントで判断待ちか回答済みかを決める。担当中 (`in_progress`) などのチケットも回答済みの一覧に出す
