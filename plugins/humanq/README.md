# humanq — 判断待ちの画面

beads (bd / br) のチケットのうち、ユーザーの判断が要るもの (`human` ラベル) を、この端末の全プロジェクト分まとめて `http://127.0.0.1:8765/` の画面に出す。ユーザーは手が空いたときに画面を開いて答えるだけでよく、エージェントは問いをチケットに書いておくだけで、会話を止めずに先へ進める。

## 目的と限界

- 自律的に長く動くエージェントが、人の判断を待つたびに会話を止めないための道具。判断待ちを AskUserQuestion でまとめて聞く代わりに、問いを bd に構造化して書き (下の「問いの書き方」)、人は画面で答える
- 同席している会話では、今までどおりその場で聞けばよい。この plugin はそれを置き換えない
- 守るのは「人の回答を取り違えない・二重に書かない・他のサイトから書き込ませない」こと。画面は 127.0.0.1 だけで待ち受けるが、同じ端末で動く別のプロセスからの読み書きは防がない (トークンは `GET /` のページに埋め込まれている)
- bd の CLI を 1 回の操作ごとに起動する。埋め込み Dolt の DB では、読みはサーバー側で数秒キャッシュし、書き込みは 1〜2 秒かかる

## インストール

```
/plugin marketplace add Mao-o/cc-mp-worktools
/plugin install humanq@mao-worktools
```

beads (bd / br) を使っているプロジェクト (cwd から上に `.beads/` がある) で Claude Code を起動すると、画面のサーバーが立ち上がる。ブラウザで `http://127.0.0.1:8765/` を開いておく。

## 動き

| いつ | 何をするか |
|---|---|
| SessionStart (起動・再開・`/clear`・compact) | cwd から上に `.beads/` があるプロジェクトでだけ動く。プロジェクトを登録し、画面のサーバーが動いていなければ切り離して起動する。判断待ちと回答済みの件数を Claude に伝える。ユーザーが保留にした判断待ちは判断待ちの件数に数えず、保留中の件数と、保留の期日を過ぎて判断待ちに戻った件数 (こちらは判断待ちの件数に入る) を 1 行で添える (どちらも 0 なら出さない) |
| UserPromptSubmit | このセッションで前に伝えた後に、画面で回答されたものがあれば Claude に伝える。サーバーのキャッシュを見るだけで bd は読まない |
| 画面 | 15 秒ごとに読み直す。ヘッダーの下の目次の帯に、判断待ちか回答済みがあるプロジェクトごとのチップ (名前と判断待ちの件数。判断待ちに P0 があれば「P0」の印) を出し、押すとそのプロジェクトの見出しへ飛んでフォーカスも見出しへ移る (動きを減らす設定では滑らかにしない)。件数は押した直後に変わり、空になったプロジェクトのチップは消える。幅 640px 以下ではチップを 1 行にし、帯の中だけ横にスクロールする。帯の 1 行目 (チップの上) には並びの切り替え「プロジェクトごと / 全体を優先度順」を置く (既定はプロジェクトごと。選んだほうはブラウザの localStorage に覚え、再読み込みしても同じ。覚えられないブラウザでも切り替えは効く)。「全体を優先度順」では、判断待ち (判断と作業・確認) を全プロジェクト通して優先度 → 作成日の順に 1 列に並べ、カードの head にプロジェクトの名前を出す。回答済みはその下に 1 節でまとめ (同じ順)、読めなかったプロジェクトのバナーは名前を付けて先頭に出す。この表示ではプロジェクトの見出しと目次のチップは出さない。切り替えてもカードは作り直さないので、入力中の補足・選んだ選択肢・開いた本文・フォーカスはそのまま残る。絞り込みと検索はどちらの表示にも効く。プロジェクトの見出し (名前とパス。溢れたら … で切る) は、スクロールしてもヘッダーの下に止まる。カードの head には、優先度・ID・作成日 (「作成から N 日」付き)・`human` / `answered` 以外のラベル (全文。5 個以上は先頭 4 個と「+N」) を出す。問いの背景 (`context`) は 5 行で畳み、溢れているときだけ「続きを読む」(開くと「閉じる」) を出す。開いたかどうかはカードが作り直されても保つ (スマホの幅でも最初の選択肢が最初の画面に入る)。推奨の選択肢は左に太い緑の線を引き、「推奨」を label の前に出す (最初から選んだ状態にはしない)。label の先頭の `【根本】` `【応急】` `【調査】` `【見送り】` は色付きのチップで出し、`title` に意味を出す (表示だけで、label・送る key は変えない。ほかの `【…】` は文字のまま)。回答済みのカードの本文からは、選択肢の key を外して出す。見出しは h1 (画面)・h2 (プロジェクト)・h3 (節) の順で、カードは問い (問いが無ければ題) で名前が付く。選択肢は押した状態 (`aria-pressed`) を持ち、補足欄には「補足」(選択肢が無ければ「回答」) の名前が付く。ID はボタンで、Tab で届き、押すとコピーして「コピーしました」を 1.5 秒出す。トーストの読み上げは入れ物の `aria-live` だけに任せる。選択肢と補足欄の枠は背景に対して 3:1 以上、P1 の文字は 4.5:1 以上の色にしてある (ライト・ダークとも)。「通知をオン」で、判断待ちが増えたときにデスクトップ通知が出る。キー操作: 補足欄か選択肢にフォーカスがあるとき、Cmd+Enter / Ctrl+Enter で「回答する」を押したのと同じに送る (送れない状態と IME の変換中は何もしない。素の Enter は補足欄では改行)。カードそのものにフォーカスがあるとき (回答の後はフォーカスが次のカードそのものへ移る)、数字キー (1 から選択肢の数まで) でその番の選択肢を選び (選ぶだけで送らない。同じ数字で外れない)、続けて Cmd+Enter / Ctrl+Enter で送る。カードそのものでの Cmd+Enter / Ctrl+Enter は、そこで数字を押して選んだ後だけ効く (送った直後の押し直しやキーのリピートで、次のカードの前からある下書きの選択を送らない)。補足欄の中の数字は普通の入力。「回答する」の隣に「⌘↵ / Ctrl+↵ で送信」を出す。書き込めないプロジェクトのカードでは、どのキーも何もしない。「回答する」を押すとカードが畳まれ、送信は裏で行う。成功すると「「<題>」に回答しました: <選んだ選択肢>」のトーストが出て、その「取り消す」で判断待ちに戻せる (ページの下の回答済みのカードまでスクロールしなくてよい。取り消しが失敗したときもトーストで知らせる)。ほかのタブ・セッションで取り消して答え直されていた回答は、トーストからもカードからも取り消さず、「取り消しませんでした。この回答はもう最新ではありません」と知らせて読み直す (下の「回答の形」の回答の署名)。失敗したら読み直し、書き込まれていなければ同じカードが赤い枠で戻る (エラーの全文はカードの中)。トーストは右下に出る (幅 640px 以下では下に全幅で出し、ページの下に同じ高さの余白を足す)。入力中の下書きは再読み込みしても残る。入力中のカードは、問いが書き換わっても作り直しを後回しにする。その間に回答を押しても、問いが変わっていれば送らずに作り直し、「問いが更新されました。見直してから送ってください」と知らせる (選んだ選択肢は消え、補足は残る)。読み込みが 2 回続けて失敗すると、消えない案内に「画面のサーバーに届きません。最後に読めたのは hh:mm です。自動で読み直しています」と「今すぐ読み直す」を出し、ヘッダーの更新時刻に「(古いデータ)」を付ける (読めたら両方消える。1 回の失敗ではトーストだけ)。サーバーが入れ替わった旨の案内 (再読み込みを求めるもの) は、この案内に上書きされず、読めても消えない。読めなかったプロジェクトのバナーは「読めませんでした (最後に読めたのは hh:mm。自動で読み直します): <エラー>」と出す (一度も読めていなければ時刻の部分は出さない)。判断待ちの件数に上限は無い。多いときは、目次の帯の下の絞り込みと検索で探す: 検索欄 (題・問い・背景・選択肢の label・チケット ID の部分一致。大文字小文字を区別しない)、プロジェクト・種別 (判断 / 作業・確認 / 問いなし)・優先度・ラベル (`human` / `answered` 以外の全ラベルを全文で)。選べる値が 2 つ以上ある部品だけ出す。絞り込みは回答済みにも効く。絞り込むと「N 件中 M 件を表示」(N は判断待ちの全件、M は表示中の判断待ち) と「解除」が出る。ヘッダーの件数・タブのタイトル・デスクトップ通知・hook の件数は、絞り込みに関係なく全件を数える。状態は URL の query (`?project=<パス>&kind=decision|task|none&prio=<数>&label=<ラベル>&q=<語>&snoozed=hide`) に持ち、再読み込みしても残る (関係ない query は触らない)。検索欄は 15 秒ごとの読み込みで作り直さず、入力もフォーカスも保つ。隠したカードの下書きと失敗の表示は残る。絞り込みは画面の側だけで、サーバーと bd / br の読み書きは変わらない |
| 画面の「保留」 | 今は答えない判断待ちを、期日まで (または期限なしで) 脇へ置く。判断待ちのカードの「保留」(「回答する」の隣) で欄を開き、期間 (明日まで / 3 日 / 1 週間 / 期限なし) か「日付を選ぶ」(今日以降) を選び、補足 (任意。何を待っているか) を書いて「保留する」で送る (選ぶだけでは送らない。「やめる」か Escape で閉じる)。「N 日後にリマインド」は「N 日後まで保留」と同じ。日付はブラウザのローカルの日付で数える。カードは判断待ちから外れ、ページの下の畳んだ節「保留中 (N)」に、期日の早い順 (期限なしは最後) で出る (どちらの並びでも 1 つの節で、head にプロジェクトの名前を出す)。保留中のカードには期日 (「あと N 日」付き)・補足・「保留を解除」を出し、回答の部品は出さない (答えるときは解除して判断待ちに戻す)。成功のトースト「「<題>」を保留しました (<期日>)」の「解除」でも戻せる。期日はその日の終わりまでで、翌日の読みで判断待ちに戻り、カードに「保留の期日 (<日付>) を過ぎて判断待ちに戻りました」と補足を出す。保留中はヘッダー・タブのタイトル・デスクトップ通知・hook の判断待ちの件数に数えない。期日を過ぎて戻ったものは数え、「判断待ちが増えました」の通知も出る (自分で解除したものは通知しない)。絞り込みの「保留中」(含める / 含めない。URL の `snoozed=hide`) で保留中の節ごと隠せる (保留中が 1 件も無ければ出さない)。検索とほかの絞り込みは保留中のカードにも効く。回答済みのカードと書き込めないプロジェクトのカードには「保留」を出さない。失敗の扱い (戻したカードに選択と補足が残る・ラベルだけの失敗は「保留は記録済み」と知らせる) は回答と同じ |

- `.beads/` の無いプロジェクトでは何もしない
- サーバーは 1 台を全プロジェクト・全セッションで共有する。ポートを取れたものだけが残るので、同時に起動しても 1 台になる。動いているサーバーが hook の版 (`plugin.json` の `version`) より古い (または版が読めない) と、次の SessionStart で入れ替わる。新しい版のサーバーは止めない (plugin を上げたあとも、上げる前から動いているセッションは旧版の hook で SessionStart を出すので、版が違うだけで入れ替えると新旧が交互に入れ替わる)。書き込みのトークンは state のファイルに保存するので、入れ替わっても開いたままの画面で回答できる
- 入れ替えの判断は、動いているサーバーの `server.json` (state dir) の pid を見て止める。state dir の違うサーバー (別の marketplace から入れた同じ plugin など) は止められず、新しいサーバーはポートを取れずに終わる。そのときは古いサーバーの pid を kill してから Claude Code を起動し直す
- 状態は `${CLAUDE_PLUGIN_DATA}` に置く: `projects.json` (登録したプロジェクト)・`server.json`・`server.log`・`token` (書き込みのトークン、0600)・`sessions/` (セッションごとに伝えた回答)
- 待ち受けは 127.0.0.1 だけ。書き込みは画面に埋め込んだトークンと Host の検査を通ったものだけ受け付ける。ほかのサイトの iframe には入れられない
- ポートは `HUMANQ_PORT` で変えられる (hook の env)
- プロジェクトごとに、`.beads/` の中のファイルの印で bd か br かを決める (CLI は打たない)。br の印は `.beads/.gitignore` の `.br_history` か `fsqlite` を含む行・`.br_history/`・`*-fsqlite-ns-*`・`.br-db-*.lock`、bd の印は `metadata.json` の `database` か `backend` が `dolt`・`embeddeddolt/`。br の印だけなら br、bd の印だけなら bd、印が無ければ bd。両方ある・どちらの印も無く SQLite の形 (`metadata.json` の `database` が `.db` で終わる) のときは決められないので、どの CLI も打たず、画面に理由を出す
- hook の env `HUMANQ_BEADS_CLI` (`bd` / `br` / `auto`、未設定は `auto`) で決め方を指定できる。`HUMANQ_PORT` と同じくプロジェクトの settings の `env` でプロジェクトごとに決められる。指定に反する印があれば決められない扱い。`bd` / `br` / `auto` 以外の値は `auto` として扱い、SessionStart で 1 行だけ警告する
- 同じ beads の DB に届く登録は、画面に 1 つのプロジェクトとして出す (同じ問いを 2 枚出さない)。br のプロジェクトを git worktree で開くと、hook は worktree の dir を登録するが、br は worktree の最上位の `.beads/` に DB (`metadata.json` の `database` か `beads.db`) が無ければ本体の worktree の `.beads/` を読み書きする (br 0.7.6 で実測)。この登録は本体のパスにまとめる (本体のセッションを開いていなくても本体のパスで出す)。`.beads/` が同じ dir を指す登録 (symlink 越し・大文字小文字だけ違うパス) も 1 つにする。worktree が自分の DB を持つ・`.beads/redirect` がある・`.beads/` が worktree の下の dir にある・bd のプロジェクト (bd の worktree の解決は測っていない) は、まとめない。回答・取り消しの書き込みは、同じ git の repo (本体と worktree) のプロジェクトどうしで 1 本ずつにする (まとめない bd の worktree の 2 枚から同時に答えても、二重に書かない)。`.git` はファイルを読むだけで git は打たない。登録のファイル (`projects.json`) の形は変えず、まとめるのはサーバーが読むときだけ (前の版が別々に登録したものも 1 つに読む)
- br のプロジェクトも、bd と同じに画面で回答・取り消しができる (書き込みの形・失敗の段階・送り直し・署名の照合は下の「回答の形」のとおりで、bd と同じ)。hook は件数に加えて、問いの置き方と回答の拾い方を br のコマンドで案内し、bd のコマンドは出さない。どちらか決められないプロジェクト (unknown・conflict) では、件数は出さず、読めない理由と設定の案内だけを出す
  - 読みは 1 プロジェクトあたり 3 プロセス: `br list -l human` と `br list -l answered` (どちらも `--limit 0 --json`) と、両方の ID をまとめた `br show <id...> --json`。0 件なら `show` は打たない。`show` は ID が 1 つでも無いと全体が失敗する (exit 3) ので、そのときは一覧から 1 回だけ読み直す
  - 回答は 5 プロセス: `br list -l human` → そのチケットの `br show <id> --json` (問いの署名の照合と、送り直しの判定のコメントを 1 回で読む) → `br --actor user/humanq comments add <id> -f <file>` → `br --actor user/humanq label add <id> answered` → `br --actor user/humanq label remove <id> human`。取り消しは `br list -l answered` → `br show <id> --json` → `comments add` → `label add <id> human` → `label remove <id> answered`。保留は `br list -l human` → `br show <id> --json` → `comments add` → `label add <id> snoozed`、保留の解除は `br list -l human` → `br show <id> --json` → `comments add` (最後の `[humanq]` コメントが保留のときだけ) → `label remove <id> snoozed` (付いているときだけ)。br の `label` は、付いている (`exists`) か付いていない (`not_found`) ときも exit 0 で終わるので、成功とみなす
  - 一覧は status で絞らない (`-s` を付けない)。br の `list` の既定は `closed` と `tombstone` (`br delete` したもの) だけを除くので、利用者が `br list -l human` で見る判断待ちと同じものが画面と hook の件数に出る: `deferred`・`draft`・`pinned` と、br が宣言なしで受け付ける独自の status (`review` など) のチケットも出る。回答済み (`answered`) の側も同じ。bd の回答済みの読みも status で絞らない (`bd list --label answered`。既定が `bd human list` と同じ status を出すので、`hooked` や独自の status のチケットも回答済みに出る)
  - 問いは `show` の `agent_context` (JSON の文字列) の top-level の key `humanq` から読む (形は bd の metadata の `humanq` と同じ)。`agent_context` が JSON の object でない・`humanq` が無い・`ask` が文字列でないときは「問いが未整理」として出す
  - コメントの並びは br では決まっていないので、`created_at` の順 (同じ秒なら ID の順) に並べてから、最後の `[humanq]` コメントを回答として読む (両ラベルのチケットの向き・送り直しの判定・取り消しの署名の照合も同じ並びで読む)
  - br はプロジェクトの dir を cwd にして起動する (br に `-C` は無い)。DB・`.beads`・JSONL の場所を指す env (`BEADS_DB`・`BD_DB`・`BD_DATABASE`・`BEADS_DIR`・`BEADS_JSONL`) は br に渡さない (残っていると、登録したプロジェクトではない DB を読むため)
- 保留 (`snoozed` ラベル) の付いた判断待ちは、期日を読むために読みのたびにコメントも読む。bd は 1 件ごとに `bd comments <id> --json` を 1 プロセス足す (保留が無ければ今までと同じ打ち方)。br は読みの `show` が返すコメントから読むので、プロセスは増えない。保留・保留の解除の書き込みは、回答と同じく代表のパスで、同じ git の repo のプロジェクトどうしで 1 本ずつ行う
- br を bd の `.beads/` に向けて打つと、エラーを出さずに空の一覧を返して `.beads/` に dolt のファイルを作るので、br と確定した dir にしか打たない
- サーバーはセッションが終わっても動き続ける。止めるときは `server.json` の pid を kill する

## 問いの書き方 (`human` を付けるときは必ず書く)

bd ではチケットの metadata の `humanq`、br では `agent_context` の top-level key `humanq` に置く (JSON の形は共通)。画面はこれを読んで、問い・背景・選択肢のボタンを出す。無いチケットは「問いが未整理」として本文だけが出て、自由記述でしか答えられない。

```json
{"humanq": {
  "v": 1,
  "kind": "decision",
  "ask": "1 文の問い。チケット本文を読まなくても答えられること",
  "context": "2〜5 行。何が起きているか・選ぶと何が変わるか・判断の軸",
  "options": [
    {"key": "a", "label": "【応急】15 字程度", "desc": "選んだら何をするか"},
    {"key": "b", "label": "【根本】...", "desc": "..."}
  ],
  "recommended": "a"
}}
```

- `kind`: `decision` (方針の判断) / `task` (ユーザーの手が要る作業や確認。回答には結果を書いてもらう)
- `options` は 2〜4 個で、互いに排他にする。選択肢に無い答えは補足欄に書かれる
- `recommended` は推奨の key。推奨が無ければ書かない
- `label` は 15 字程度。下の深さのラベルを付けるときは、ラベルも字数に含める (`【見送り】` だけで 5 字使う)
- 文中の `` `...` `` はコード表記になる
- 入れ方 (bd): JSON をファイルに書いて `bd update <id> --metadata @<file>`。`--metadata` は metadata 全体を置き換えるので、ほかのキーがあれば一緒に書く。`--set-metadata` は値を文字列として入れてしまうので使わない
- 入れ方 (br): `br show <id> --json` で今の `agent_context` を読み、ほかの key を残したまま `humanq` を足した JSON をファイルに書いて `br update <id> --agent-context @<file>`。`--agent-context` も値を丸ごと置き換える。今の値の半分未満に短くなる・空になる書き換えは `--force` が要る (残すべき key を落としていないか確かめてから付ける)
- br で `.beads/config.yaml` の `inherited_context.enabled` を有効にしていると、`agent_context` は子のチケットの `show` / claim にも出るので、問いが子の作業に混ざる (既定の config にこの key は無く、無効)

### 選択肢の深さのラベル

不具合・障害・設計上の問題への対処方針を問うときは、各選択肢の `label` の先頭に、対処の深さを示すラベルを付ける。付けないと「直す」選択肢が原因を取り除くのか症状を抑えるだけなのかが、`desc` を読み比べないと分からない。1 つの問いの中では、全選択肢に付ける。

| ラベル | 付ける条件 |
|---|---|
| 【根本】 | 原因を取り除き、同じ症状が再発しない |
| 【応急】 | 症状は止まるが原因は残る。`desc` に、残る原因と後で要る作業を書く |
| 【調査】 | まだ直さず、原因の特定や再現を先にする |
| 【見送り】 | 今は何もしない (許容する・後に回す) |

- 手順の選び方を聞く問い (`kind: task` の確認作業など) のように、深さで分かれない問いには付けない
- 推奨したい選択肢を【根本】に寄せて分類しない。原因が一部でも残るなら【応急】にする。【応急】を推奨するなら、今それで良い理由を `desc` に書く
- 画面は、この 4 語 (`【根本】` `【応急】` `【調査】` `【見送り】`) が `label` の先頭にあるときだけ、チップにして出す
- ラベルは `label` に入れる。サーバーは選択肢から `key` / `label` / `desc` だけを取り出すので、別のフィールド (`tag` など) に入れると黙って捨てられる
- 回答のコメントは `[humanq] 回答: 【応急】設定で無効化 (a)` のようになり、どの深さの対処を選んだかが判断の記録に残る
- `label` は問いの署名 `qsig` に入る。判断待ちの既存の問いに後からラベルを足すと、開いている画面からの回答が 409 `changed` になる。既存の問いは書き換えず、新しく書く問いから付ける

## 回答の形 (画面が書く)

- コメント 1 件: 1 行目が `[humanq] 回答: <label> (<key>)`。補足があれば空行の後に続く。自由記述だけのときは `[humanq] 回答: (自由記述)`。作者は `user/humanq`
- ラベル: `answered` を足してから `human` を外す (各段階は 1 回だけ再試行する)。close はしない
- 取り消し (反映前だけ): `[humanq] 取り消し` のコメントを付け、`answered` を `human` に戻す。画面は取り消す回答の署名 `asig` を付けて送る。サーバーは今の最後の `[humanq]` コメントの署名と照合し、違えば (ほかのタブ・セッションで取り消して答え直された後に、前の回答のトーストやカードから押した) 何も書かずに 409 `{code: "stale"}` を返す。`asig` を送らない画面からの取り消しは、今までどおり照合せずに受け付ける
- 回答の署名 `asig`: そのコメントがチケットの何件目の `[humanq]` コメントかと、その本文から作る (同じ選択肢で答え直しても、前の回答とは違う値になる。エージェントのコメントは数えないので、間に挟まっても変わらない)。`/api/answer` の成功の応答 (`{ok: true, asig}`) と、回答済みの一覧 (`/api/items` の `answered`) の各チケットに入る。回答のトーストの「取り消す」は応答の値を、回答済みのカードの「取り消して判断待ちに戻す」は一覧の値を送る。一覧でコメントを読めなかったチケットの署名は空で、どの回答とも合わない (そのカードからの取り消しは断られ、読み直すと直る)
- 送り直しても壊れない: チケットの最後のコメント (全体) が同じ本文の `[humanq]` コメントで 10 分以内なら、コメントは書かずにラベルだけ直す (途中で失敗した書き込みを、画面から送り直しても回答が二重にならない)。間にほかのコメント (エージェントの問い直しなど) が挟まっていれば、新しい回答として書く
- 画面は回答に、見ていた問いの署名 `qsig` を付ける (問い・背景・選択肢の key と label と並び・推奨から作る。選択肢の説明 `desc` だけの直しは含めない)。今の問いと違えば書き込まず、409 `{code: "changed"}` を返す。`qsig` を送らない画面からの回答は、今までどおり受け付ける
- `human` と `answered` が両方付いたチケットは、書き込みの途中か、ラベルの付け替えに失敗したもの。画面は最後の `[humanq]` コメントで向きを決める: 取り消し・保留・保留の解除なら判断待ち、回答 (または `[humanq]` コメントが無い) なら回答済み
- 保留 (判断待ちのまま、期日まで脇へ置く): コメント 1 件の 1 行目が `[humanq] 保留: <YYYY-MM-DD> まで` (期限なしは `[humanq] 保留: 期限なし`)。補足があれば空行の後に続く。作者は `user/humanq`。ラベル `snoozed` を足す (1 回だけ再試行する)。status・担当・`human` ラベルは変えない。`/api/snooze` の body は `{project, id, qsig, until, note}` で、`until` は今日 (サーバーの端末のローカルの日付) 以降の `YYYY-MM-DD` か `null` (期限なし)。問いの署名 `qsig` の照合と送り直しの扱いは回答と同じ
- 正本はコメントで、ラベルは読むチケットを絞る印: 保留中と読むのは、`snoozed` ラベルが付き、最後の `[humanq]` コメントが保留の形 (日付として読める) のときだけ。ラベルだけ・コメントだけ・形の崩れた保留は判断待ちに出す (保留と確かめられないものを隠さない)
- 期日はその日の終わりまで。期日を過ぎると、次の読みで判断待ちに戻る (`/api/items` の判断待ちの各件の `snooze` に `{until, note, expired: true}` が入る)。ラベルは残るが期日で読み、次に回答・保留の解除をしたときに外す
- 保留の解除: `[humanq] 保留の解除` のコメントを付け、`snoozed` を外す (`/api/unsnooze` の body は `{project, id}`)。最後の `[humanq]` コメントが保留でなければコメントは書かず、ラベルが付いていなければ外さない (送り直し・ほかで解除済みでも二重に書かない)
- 回答済み (`answered`) と、判断待ちに無いチケットは保留できない (400 `{code: "gone"}`)。`/api/items` の各プロジェクトの `snoozed` に保留中のチケット (期日の早い順。`snooze` に `{until, note, expired: false}`) が入り、`human` には入らない。`/api/summary` の `human` も保留中を数えず、`snoozed` (保留中の件数) と `returned` (期日を過ぎて戻った件数) を返す
- `/api/answer`・`/api/undo`・`/api/snooze`・`/api/unsnooze` の処理中に起きた失敗の応答 (400・409・500・502) には、送信の種類 `op` (`answer` / `undo` / `snooze` / `unsnooze`) を入れる。画面は `op` で文言を分ける (回答の失敗と取り消しの失敗を取り違えない)
- エージェントは `user/humanq` を名乗らず、コメントの先頭に `[humanq]` を書かない (人の入力と見分けるため。回答の署名も `[humanq]` のコメントの件数で数える)

## 回答を拾う

手順は bd と br で共通で、コマンドだけが違う。`answered` ラベルの付いたチケットの各件について (一覧は status で絞らない。`open` だけにすると、担当中 (`in_progress`) のチケットに問うのは普通なので、回答したチケットが拾えない。bd・br とも CLI の既定が `closed` などの終わったものだけを除き、画面と同じ範囲を出す):

| | bd | br |
|---|---|---|
| 一覧 | `bd list --label answered --flat -n 0` (`--status` を付けない。既定は `bd human list` と同じ status を出し、`hooked` や独自の status のチケットも拾える。`closed` は出ない) | `br list -l answered --limit 0 --json` (`-s` を付けない。既定は `closed` と `tombstone` だけを除くので、`deferred`・`draft`・`pinned` と独自の status (`review` など) のチケットも拾える。`--limit 0` は件数の上限を外す。結果の `issues` の各件) |
| コメントを読む | `bd comments <id>` | `br comments <id> --json` |
| ラベルを外す | `bd label remove <id> answered` | `br label remove <id> answered` |

1. コメントの最後の `[humanq] 回答` を読む (その後に `[humanq] 取り消し` があれば飛ばす)。**br ではコメントの並びが決まっていない** (JSONL から取り込み直すと古いコメントが後ろに来ることがある) ので、`br comments <id> --json` の件を `(created_at, id)` の昇順に並べ直してから、最後の `[humanq]` コメント (作者 `user/humanq`) を読む。生の並びの最後を読むと、古い回答を拾う
2. 回答に従ってチケットを直す (DoD・優先度・担当の書き換え / close など)
3. `answered` を外す (`human` も付いていたら、それも外す)
4. 回答が読めない・決めきれないときは、問いを書き直して `answered` を `human` に戻す (問い直しも画面に出る)。**問い直すときは、何を変えたかをコメントに書く** (コメントが無いと、最後のコメントが前の回答のままなので、同じ選択肢を 10 分以内に押された新しい回答が「送り直し」とみなされて記録されない)

作業を選ぶ一覧からは `answered` も除くこと。反映する前に作業に入らないため。

保留 (`[humanq] 保留: ...` のコメントと `snoozed` ラベル) は回答ではない。ユーザーが「今は答えない」と決めた判断待ちで、`human` も status も担当もそのまま残る。エージェントは:

- 回答を待つ。保留を理由に、問いを取り下げたり、答えを推測して進めたりしない (期日を過ぎれば判断待ちに戻り、hook の件数にも入る)
- `snoozed` ラベルを外さず、保留・保留の解除の `[humanq]` コメントを書かない (どちらもユーザーが画面でする)
- 問いの前提が変わって問い直すときは、今までどおり問いを書き直し、何を変えたかをコメントに書く (保留は続き、書き直した問いは保留が明けたときに出る。急ぐなら、同席している会話でユーザーに保留の解除を頼む)

## 外部送信

なし。マシンの外へは何も送らない。

- 画面のサーバーは 127.0.0.1 で待ち受け、ブラウザとだけ話す。外部の CDN などから script や style を読まない (CSP で `default-src 'none'`)
- bd の CLI (`bd human list`・`bd list`・`bd comments`・`bd label` など) と br の CLI (`br list`・`br show`・`br comments add`・`br label`) を、登録したプロジェクトのディレクトリで起動する。DB への書き込みは、画面で回答・取り消し・保留・保留の解除を押したときだけ。ただし br は読みでも、JSONL の方が DB より新しいと DB へ取り込む (br の既定の動き。利用者が `br list` を打ったときと同じ)
- hook の出力 (判断待ちの件数・回答のあったチケットの ID) は Claude Code の会話に入る

## 要件

- macOS / Linux。Python 3.11 以上 (標準ライブラリだけを使う)。登録のファイルロックに `fcntl` を使うので Windows では動かない
- bd (1.x、`bd human` があるもの) か br (0.7.6 で確認) のどちらかが PATH にあること。`.beads/` が無いプロジェクトでは何もしない
- 画面はモダンなブラウザ (Chromium で確かめている)

## テスト

```
cd plugins/humanq
python3 -m unittest discover tests        # サーバー (bd の読み書きは偽の bd だけで回す。PATH に bd があっても本物は打たない)
HUMANQ_TEST_BD=bd python3 -m unittest discover -s tests   # 本物の bd の脚も回す (bd を上げたら手元でこれを回す)
PLAYWRIGHT_PATH=<playwright の index.mjs> node tests/ui_test.mjs   # 画面 (Playwright と chromium が要る)
```

`tests/test_server.py` の bd を通すシナリオ (送り直し・ラベルの再試行・両ラベルの向きなど) は、`tests/fake_beads.py` (偽の bd) を一時の bin dir に置いて回すので、本物の bd が無い環境でも skip されない。偽物は bd 1.3.4 で実測した癖 (0 件の `human list --json` は `null` など) を持ち、失敗は env (`FAKE_BEADS_FAIL`) で注入する。サーバーが打つ bd の argv の列 (読み・回答・取り消し) も、このテストで固定している。discover で流すと、このシナリオは別のプロセスで並列に回る (`HUMANQ_TEST_JOBS`、既定 3。`HUMANQ_TEST_JOBS=1` で直列。クラスやテストを名前で指したとき (`python3 -m unittest test_server.WithFakeBd` など) も直列)。

br のプロジェクトの読み (一覧と `show` の argv・終わっていない status のチケットが全部出ること・コメントの並べ替え・両ラベルの向き・bd を打たないこと・hook の案内) は、`tests/test_br_read.py` が同じ偽物を br の名前で置いて回す (偽の br はコメントを新しい順で返す)。回答・取り消しは、`tests/test_server.py` の `WithFakeBr` が bd と同じシナリオを偽の br で回し、サーバーが打つ br の argv の列も固定している。

`tests/test_cli_contract.py` は、bd・br の CLI の癖 (0 件の出力の形・拒否される flag・metadata の形・コメントの並びと id など) を、偽の bd・偽の br・本物の bd・本物の br の 4 通りに同じ assertion で当てる契約テスト。br は、画面の読み (`BrBackend.load`) の thread が書いた順で返ること (同じ秒のコメント・時刻をずらしたコメント・本物は JSONL から取り込み直した後のコメント、0 件は `[]`) と、偽の br が断る形を本物の br も断ること (偽物が通さない形を本物が通す食い違いの検出) もここで当てる。保留と保留の解除は、ラベルの段階の失敗を humanq の差し替え口から注入した送り直しで、コメントが二重にならず・ラベルが付いて外れ・status と担当が変わらないことを、4 通りで当てる。偽物 2 通りは既定の suite と CI で走る。本物は遅い (bd だけで 30 秒近い) ので、PATH に bd / br があっても既定では起動せず skip する (理由に変数名を出す)。手元で回すときは env `HUMANQ_TEST_BD` / `HUMANQ_TEST_BR` を立てる (値は起動コマンド。`bd` / `br`、前置き付きの `<launcher> -- br`、PATH のを使うなら `1`)。本物は一時 dir の使い捨てのプロジェクトでだけ打ち、利用者のプロジェクトには触れない。**bd か br を上げたら、env を立てて手元で契約テストを回す** (`HUMANQ_TEST_BD=bd HUMANQ_TEST_BR=br python3 -m unittest tests.test_cli_contract`) (食い違うと、どの CLI のどの版のどの癖かを失敗の文に出す)。

同じ DB に届く登録のまとめ方 (git worktree・symlink 越しの `.beads/`・大文字小文字だけ違うパス・前の版の登録のファイル・2 枚からの同時の回答) は、`tests/test_same_db.py` が手で作った `.git` の形と本物の git の worktree、偽の br・偽の bd で確かめる。br を worktree で打ったときに届く DB は、契約テストが偽の br と本物の br に同じ assertion で当て、humanq の判定が同じ dir を返すことも確かめる。

`tests/ui_test.mjs` はサーバーを一時ポートと一時 state dir で起動し、API の応答を台本どおりに返して画面の動き (押したカードの即時の非表示・失敗時の戻し・入力中の保護など) を確かめる。bd には触れない。
